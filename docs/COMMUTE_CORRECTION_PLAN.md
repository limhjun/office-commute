# 퇴근 시각 정정 및 월 마감 구현 계획

- 작성일: 2026-10-09
- 대상: GitHub Issue #52 — 퇴근 시각 정정 기능 구현
- 상태: 운영 정책 확정. API·DB·저장 방식의 기술 계약은 미확정이며, 기능 구현은 명시적인 구현 요청 이후 진행한다.
- 원칙: 기존 `controller → service → repository` 구조와 `CommuteHistory`의 행 단위 출퇴근 기록 방식을 유지한다.

## 0. 세션 검토 기준과 문서의 역할

- 검토 출처: [Issue #52 설계 세션](thread://01a11f40-c5d2-7621-9ca2-6809843e8478?hostId=local). 2026-10-09에 처음부터 마지막 사용자 확인까지 대조했다.
- 대화 중 제시된 대안보다 뒤에 확정한 정책을 우선한다. 월 마감을 2차로 미루기, 정정 신청 후에만 새 출근 허용하기, 대기 신청 내용 덮어쓰기, 상시 마감 해제는 최종 채택한 방안이 아니다.
- 원 세션에서 일시적으로 작성한 미완성 코드·마이그레이션은 되돌렸다. 당시 제안한 API·테이블을 확정 계약이나 구현 완료 근거로 사용하지 않는다.
- 이 문서는 정책 합의와 후속 구현의 인계 기준이다. 이번 보완은 문서 변경이며, 운영 데이터 정정·월 마감·보고서 발송을 실행한 것이 아니다.
- 1~3장의 운영 정책은 확정됐다. 아래 기술 설계 항목은 정책을 구현하기 위한 작업이며, 필드명·잠금 방식 등을 다시 운영 정책 질문으로 돌리지 않는다. 합의된 동작이나 범위를 바꾸어야 하는 경우에는 별도로 설명한다.

## 1. 확정된 정책

### 1.1 출근과 일반 퇴근

| 항목 | 정책 |
| --- | --- |
| 과거 미퇴근 기록 | 정정 신청·승인 여부와 관계없이 새 근무일의 출근을 허용한다. |
| 같은 근무일 재출근 | 기존 직원·근무일 UNIQUE 제약과 하루 한 기록 정책을 유지한다. |
| 일반 퇴근 대상 | 가장 최근에 시작한 실제 근무 기록만 대상으로 한다. 연차 기록은 제외한다. |
| 일반 퇴근 허용 시간 | 출근 시각부터 정확히 24시간까지 허용한다. 이를 초과하면 정정 승인이 필요하다. |
| 최신 근무가 이미 종료됨 | 일반 퇴근을 거부한다. 이전 미퇴근 기록을 대신 종료하지 않는다. |
| 후속 출근이 있는 미퇴근 | 24시간 이내라도 일반 퇴근 대상에서 제외하고 정정 필요로 표시한다. |
| 누락된 퇴근 시각 | 자동으로 추정하거나 다음 출근 시각으로 채우지 않는다. |
| 야간근무 | 날짜가 바뀌어도 최신 근무이고 24시간 이내라면 일반 퇴근할 수 있다. |

### 1.2 정정 신청과 이력

- 본인 기록만 정정 신청할 수 있다.
- 미퇴근 기록에 실제 종료 시각을 등록하는 신청과, 완료된 기록의 종료 시각 변경을 지원한다.
- 완료된 기록의 종료 시각은 앞당기거나 늦출 수 있다. 아래 시각 검증 조건은 두 경우에 동일하게 적용한다.
- 최근 N일·N개월 같은 별도 정정 기한은 두지 않는다. 해당 기록이 마감된 보고서의 보호 범위에 포함되는지로 판단하며, 신청과 승인 시점 모두 검사한다. 기존 발송 월의 초기 전환은 3.3절을 따른다.
- 정정 사유는 필수다.
- 반려 사유도 필수다. 승인 의견은 선택 사항이다.
- 한 근태 기록에는 승인 대기 요청을 하나만 허용한다.
- 제출한 요청의 시각·사유를 덮어쓰지 않는다. 내용 변경은 취소 후 재신청한다.
- 신청자는 대기 요청을 취소할 수 있다. 승인·반려·취소된 요청은 변경하지 않는다.
- 취소된 요청도 이력으로 남긴다. 신청·반려·취소는 원본 근태를 변경하지 않는다.
- 승인 시에만 같은 근태 행의 종료 시각과 근무 분을 함께 갱신한다.
- 반복 정정은 매번 새 요청으로 남기고, 승인 당시의 변경 전후 값을 보존한다.

정정된 종료 시각은 다음 조건을 모두 만족해야 한다.

1. 출근 시각 이상이다. 출근과 동일한 시각은 기존 규칙대로 허용한다.
2. 현재 시각 이하이다.
3. 후속 실제 근무가 있으면 그 출근 시각 이하이다.
4. 연차 기록이 아니다.

일반 퇴근의 24시간 제한은 승인 정정에는 적용하지 않는다. 실제 26시간 근무했다면 사유를 제출하고 승인받아 기록할 수 있다. 시간은 UTC `Instant`로 비교하고, 근무일·표시는 기록에 보존된 `workDate`·`workZone`을 사용한다.

### 1.3 승인 권한과 담당자 지정

상위 승인자 역할의 이름은 가칭 `COMMUTE_APPROVER`다.

| 정정 대상 | 승인 담당자 |
| --- | --- |
| 일반 직원 | 근태 관리자(`MANAGER`) |
| 근태 관리자 | 지정된 상위 승인자 |
| 상위 승인자 | 지정된 근태 관리자 |

- 모든 역할은 본인 출퇴근·근태 조회·정정 신청을 사용할 수 있다.
- 자기 승인은 항상 금지한다.
- 상위 승인자는 지정된 대상의 정정 요청과 관련 이력만 조회·승인·반려할 수 있다.
- 상위 승인자에게 직원·팀 관리, 전체 초과근무 보고서 등 기존 관리자 권한을 부여하지 않는다.
- 근태 관리자가 승인 담당자를 지정한다. 관리자와 상위 승인자는 서로 다른 역할의 담당자를 지정한다.
- 본인을 승인자로 지정할 수 없다. 담당자가 없으면 관리자·상위 승인자의 요청은 승인할 수 없다.
- 해당 직원의 승인 대기 요청이 있으면 그 직원의 지정 승인자를 변경할 수 없다.
- 담당자 변경이 필요하면 대기 요청 취소 → 담당자 변경 → 재신청으로 처리한다.
- 대기 요청의 신청자·지정 승인자에게 영향을 주는 역할 변경·계정 비활성화도 요청을 먼저 승인·반려·취소한 뒤 허용한다. 무관한 직원의 변경까지 막지 않는다.
- 일반 직원에게 별도의 지정 승인자·팀별 승인 제한을 추가하는 것은 이번 범위에 포함하지 않는다.

관리자와 상위 승인자가 서로 승인할 수 있으므로, 자기 승인은 방지하지만 독립적인 제3자 검토까지 보장하는 구조는 아니다.

### 1.4 월 마감과 최종 보고서 발송

```text
근태 기록 및 정정 신청
→ 미퇴근·승인 대기 요청 해결
→ 근태 관리자의 수동 월 마감
→ 근태 기록 잠금
→ 최종 보고서 생성·발송
```

- 근태 관리자만 월 마감을 수행한다. 상위 승인자는 마감할 수 없다.
- 회사 달력 `Asia/Seoul` 기준으로 종료된 과거 월만 마감한다. 진행 중인 월과 미래 월은 마감할 수 없다.
- 마감 자체에 별도 승인 절차를 두지 않는다. 담당자와 시각을 저장한다.
- 실제 집계 입력 기간에 미퇴근 또는 승인 대기 요청이 남아 있으면 마감할 수 없다.
- 마감 이후에는 관리자도 해당 기록을 정정할 수 없다.
- 보고서가 참조하는 전월 말 기간도 보호한다. 근태 갱신뿐 아니라 집계 입력을 바꾸는 기록 추가·삭제도 차단한다.
- 최종 보고서는 월 마감 완료 후 발송한다.
- 마감 전 Excel 다운로드는 유지하되 화면·파일명에서 미마감 참고용으로 구분한다.
- 발송에 사용하는 최종 Excel 파일을 보관한다. 확정본 다운로드는 현재 데이터로 재생성하지 않고 보관본을 제공한다.
- 발송 실패 시에도 월 마감은 유지한다. 재시도는 잠긴 데이터를 대상으로 수행한다.
- 이미 발송된 보고서는 중복 발송하지 않는다.
- 마감 해제, 자동 마감, 새 알림 기능, 새 기능으로 마감한 월의 예외 정정·재발행은 이번 범위에서 제외한다. 기능 도입 전 발송 월의 일회성 정리·정정본 발송은 3.3절의 예외로 포함한다.

## 2. 기존 근태 행과 상태 모델의 관계

상태 도입은 기존 행 구조를 대체하지 않는다.

| 처리 | `workStartTime` | `workEndTime` | 표시 상태 |
| --- | --- | --- | --- |
| 출근 | 출근 시각 저장 | `null` | `IN_PROGRESS` |
| 일반 퇴근 | 변경 없음 | 현재 시각 UPDATE | `COMPLETED` |
| 미퇴근이 24시간 초과 또는 후속 출근 존재 | 변경 없음 | `null` 유지 | `CORRECTION_REQUIRED` |
| 누락 등록 승인 | 변경 없음 | 승인된 실제 시각 UPDATE | `COMPLETED` |
| 완료 기록의 정정 승인 | 변경 없음 | 승인된 실제 시각 UPDATE | `COMPLETED` |

`workingMinutes`는 종료 시각과 같은 트랜잭션에서 재계산한다. 직원 ID, 출근 시각, 근무일, 당시 시간대, 연차 여부를 변경하지 않는다.

현재도 `CommuteHistory.status(now)`는 상태를 계산한다. 변경 후에도 다음 파생 판정을 유지하는 방향이며, 별도 상태 컬럼이나 시간 경과용 스케줄러는 추가하지 않는다.

```text
연차 → DAY_OFF
종료 시각 있음 → COMPLETED
미퇴근 + (24시간 초과 또는 후속 실제 근무 존재) → CORRECTION_REQUIRED
그 외 → IN_PROGRESS
```

기존 `UNCLOSED`는 근무일이 지난 미퇴근을 의미하므로 새 규칙과 의미가 다르다. API enum, 프론트엔드 표시, 관련 테스트를 함께 변경한다. 후속 근무 판정은 조회 월에 한정하지 않는다.

정정 요청은 별도 테이블에서 다음 상태로 관리한다.

```text
PENDING → APPROVED
        → REJECTED
        → CANCELLED
```

근태 상태와 요청 상태를 하나의 enum으로 합치지 않는다. `CORRECTION_REQUIRED`는 일반 퇴근으로 해결할 수 없다는 뜻이지, 신청이 제출됐다는 뜻이 아니다. 미퇴근의 신청·반려·취소 후에도 종료 시각은 비어 있고, 완료 기록에 대기 요청이 있어도 원본 상태는 `COMPLETED`다. 화면은 근태 상태와 요청 처리 상태를 함께 표시한다.

대화 초반의 “미퇴근 기록 마감”은 한 행에 누락된 종료 시각을 승인 등록하는 뜻이었다. 이후 확정한 “월 마감”은 집계 입력 기간 전체의 변경을 잠그는 별도 처리다. API·화면·보고서 문구에서 두 의미를 구분한다.

## 3. 확정된 마감 범위와 초기 전환

아래 운영 정책은 사용자 확인을 마쳤다. 구체적인 API·DB 스키마·파일 저장 방식은 기존 아키텍처에 맞춰 기술 설계한다.

### 3.1 마감 대상 월과 회사 달력

- 종료된 과거 월만 마감할 수 있다. 진행 중인 월 마감은 이후 정상 출근과 충돌하므로 금지한다.
- 회사의 월 경계는 기존 보고서 스케줄과 같은 `Asia/Seoul`을 사용한다.
- 개인 근태의 `workDate`·`workZone`을 회사 달력으로 재해석하지 않는다.

### 3.2 마감된 보고서가 참조하는 전월 말 기록

`OverTimePeriod.rangeStart()`는 월 1일이 속한 주의 월요일이다. 따라서 월초의 주간 계산에 전월 말 근태가 포함될 수 있다. 마감한 월의 행만 보호하면 전월 말 정정으로 마감 보고서의 계산값이 바뀔 수 있다.

- 보고서가 참조하는 기간의 기록도 보호한다.
- 이전 월 전체의 마감을 선행 조건으로 요구하지 않는다. 대신 마감 검사·정정 제한에 실제 입력 기간의 겹침을 반영한다.
- 미퇴근·대기 요청의 마감 검사도 실제 집계 입력 범위와 일관되어야 한다.
- 예를 들어 2026년 9월 보고서는 8월 31일부터 9월 30일까지를 참조하므로 해당 기간을 보호한다.

### 3.3 이미 발송된 과거 보고서와 초기 전환

- 새 마감 정보가 비어 있다는 이유로 기존 발송 완료 월을 일반 미마감 월로 취급하지 않는다. 발송 이력과 운영자 확인으로 전환 대상·정정 필요 여부를 먼저 식별한다.
- 기존 발송 월은 잠그기 전에 필요한 정정을 신청·승인 절차로 처리한다. 원본을 직접 덮어쓰거나 자동으로 과거 퇴근 시각을 채우지 않는다.
- 기존 보고서는 원본으로 보존하고 수정한 보고서는 정정본으로 구분해 보관·발송한다. 수신자에게 기존 보고서 대신 정정본을 사용하도록 안내한다.
- 일회성 전환에서도 정정 완료 → 미퇴근·대기 요청 검사 → 마감·입력 기간 잠금 → 정정본 보관·발송 순서를 따른다. 발송은 마감 커밋 후 수행하고 실패해도 잠금을 해제하지 않는다.
- 집계 기간이 겹치는 과거 월은 필요한 정정을 모두 끝낸 뒤 관련 월을 잠근다. 먼저 다른 월을 잠가 아직 정리해야 하는 기록의 정정을 막지 않도록 전환 순서를 검증한다.
- 수정할 필요가 없는 기존 발송 완료 월은 확인 후 기존 발송 완료 월로 등록하고 입력 기간을 잠근다. 미발송 월은 자동 마감하지 않는다.
- 기존 `SENT`와 수신 여부가 불확실한 `DELIVERY_COMMITTED`를 구분한다. 불확실한 월은 확인 전 정정·재발송을 임시 차단하고, 시스템 밖의 발송도 운영자가 확인한다.
- 기존 발송 이력을 삭제하거나 `SENT`를 초기화해서 정정본을 최초 발송처럼 보내지 않는다. 최초 발송과 정정본의 식별·파일·발송 이력 및 중복 방지를 분리한다.
- 기존 원본 파일이 없으면 발송 메일이나 별도 보관본에서 확보한다. 현재 데이터로 재생성한 파일을 당시 원본으로 표시하지 않는다. 이미 변경된 데이터는 잠금만으로 원래 보고서와 일치하게 복원되지 않는다.
- 이번 절차는 기능 도입 전 발송 월에만 적용하는 일회성 전환이다. 새 기능으로 마감한 월의 상시 정정·재발행 경로는 만들지 않는다.

### 3.4 최종 보고서 보관과 다운로드

- 기존 보고서는 직원·팀·재직 정보 및 공휴일 정보를 다시 조회하므로 근태 잠금만으로 재생성 결과의 동일성을 보장하지 못한다.
- 기존 계산기와 Excel 생성기를 유지하고, 생성한 최종 파일을 발송 전에 보관한다. 파일 저장 실패 시 발송하지 않는다.
- 발송 재시도와 확정본 다운로드는 해당 발송 건의 보관 파일을 사용한다. 기존 원본과 전환 정정본은 서로 덮어쓰지 않는다.
- 저장 위치·파일 식별·접근 권한·백업 및 보관 운영은 기술 설계와 운영 문서에 명시한다. 기존 보고서 조회 권한을 우회하는 공개 파일 URL을 만들지 않는다.

### 3.5 9월 데이터의 일회성 전환 준비

사용자는 원 세션에서 9월 데이터에 실제 정정이 필요하다고 밝혔다. 따라서 2026년 9월을 확인 없이 먼저 잠그지 않는다. 원 세션에서 언급한 9월 2일 기록을 포함해 실제 대상 ID·기존 값·정정할 시각·사유는 운영 데이터와 신청자의 확인으로 특정하며, 대화의 예시 시각을 실제 값으로 입력하지 않는다.

| 순서 | 준비·처리 내용 | 확인할 결과 |
| --- | --- | --- |
| 1 | 기존 발송 상태, 시스템 밖의 발송, 원본 파일 확보 여부와 정정 대상 목록 확인 | 확인된 사실과 미확인 사항을 구분한 전환 목록 |
| 2 | 8월 31일~9월 30일 및 다른 전환 월과 겹치는 집계 기간 확인 | 먼저 잠그면 다른 정정을 막는 월이 없는지 확인 |
| 3 | 신청자·승인 담당자 준비 후 필요한 정정 신청·승인 | 변경 전후 이력과 수정된 근무 분, 관련 월의 재집계 결과 |
| 4 | 집계 입력 기간의 미퇴근·대기 요청 해소 후 마감 커밋 | 마감 담당자·시각과 보호 범위 |
| 5 | 최종 파일 보관 후 발송 | 이미 발송했다면 원본과 구분된 정정본·별도 발송 이력, 미발송이었다면 최초 발송 |

원 세션 마지막 답변의 마지막 질문에는 “정정본 발송 후 잠금”이라는 표현이 있었지만, 같은 답변의 절차와 앞서 확정한 정책은 **마감·잠금 커밋 후 보관·발송**이다. 전환에서도 이 순서를 적용한다. 발송 실패가 잠금을 해제하는 경로를 만들지 않는다.

## 4. 변경 범위와 아키텍처

### 4.1 backend

- `CommuteHistory`: 정정용 검증·분 계산을 일반 퇴근 검증과 분리한다. 기존 일반 퇴근의 종료 상태 보호를 제거하지 않는다.
- `CommuteHistoryService`·저장소: 이전 미퇴근에 의한 출근 차단을 제거하고, 최신 실제 근무만 일반 퇴근 대상으로 선택한다.
- 정정 도메인·서비스·저장소: 신청·승인·반려·취소, 대기 요청 중복 방지, 전후 이력을 담당한다.
- 직원 도메인·서비스: 상위 승인자 역할과 지정 관계를 추가한다. 범용 조직 계층은 만들지 않는다.
- 월 마감 도메인·서비스: 기간 검사, 수동 마감, 잠금과 이력을 담당한다.
- 보고서 발송 서비스: 모든 발송 진입점에서 마감을 확인하고 기존 발송·중복 방지 로직을 재사용한다. 최종 파일 보관·다운로드와 일회성 전환 정정본의 별도 발송 식별을 추가한다.
- 컨트롤러: 인증된 사용자 ID로 권한을 판단하고, API를 `/api/**` 아래에 둔다.
- `GlobalExceptionHandler`: 기존 오류 envelope를 유지하며 상태 충돌·권한·시각 오류를 구분한다.

### 4.2 DB 및 API

- 근태 원본의 변경 검출을 위한 버전 정보, 지정 승인자 관계, 정정 요청·이력, 월 마감 정보를 추가하는 방향이다.
- 대기 요청 하나를 보장하는 DB 제약이 필요하다. 신청 취소·처리 후 새 요청이 가능해야 한다.
- 새 Flyway 버전을 추가한다. 기존 마이그레이션을 수정하지 않는다.
- 신청 당시 원본과 승인 후 값을 보존하며, 이력을 현재 근태 값으로 재구성하지 않는다.
- API 계약에는 근태 ID·원본 버전·당시 시간대, 요청 상태, 마감·발송 상태를 포함한다.
- API 경로·필드명·DB 스키마는 정책 확인 이후 `openapi.yml`에서 먼저 확정한다.

### 4.3 frontend

- 본인 근태 화면: 정정 필요 표시, 시각·사유 신청, 요청 이력·취소.
- 승인 화면: 권한에 맞는 요청 목록, 전후 시각·근무 분·사유, 승인·반려.
- 직원 관리 화면: 승인 전용 계정 생성과 담당자 지정.
- 관리자 화면: 월 마감과 발송 결과·재시도. 잠금은 UI뿐 아니라 서버에서도 검사한다.
- 모든 역할에 본인 근태 접근을 제공하고, 상위 승인자에게 기존 관리자 화면을 열지 않는다.
- typed API client, resource별 TanStack Query hooks, 기존 오류·캐시 무효화 방식을 사용한다.
- `frontend/src/api/schema.d.ts`는 `pnpm --dir frontend gen:api`로 생성한다. 직접 편집하지 않는다.

### 4.4 구현 착수 전 작성할 기술 계약

다음은 추가 운영 정책 제안이 아니라 2단계의 산출물이다. 구체적인 경로·컬럼·저장 제품은 아직 선택하지 않았다.

| 계약 | 구체화할 내용 |
| --- | --- |
| 조회·오류 | 본인 및 승인 대상 요청·이력의 조회 범위, 근태 ID·버전·기록 시간대, 입력 오류·권한 거부·상태 충돌·마감 거부 응답과 화면 메시지 |
| 시각 입력 | 날짜와 오프셋을 포함한 입력에서 UTC `Instant`로 변환하는 규칙, 기록 `workZone` 표시, DST 중복·존재하지 않는 현지 시각 처리, DB 저장 정밀도 |
| 요청·이력 저장 | 신청 당시 종료 시각·근무 분·원본 버전, 제안 시각·사유, 신청자·처리자·처리 시각, 승인 전후 값과 반려·취소 이력. 요청 테이블이 이력을 겸할지 별도 테이블로 나눌지 명시 |
| DB 제약·경쟁 | 대기 요청 한 개를 보장하는 제약, 모든 쓰기의 버전 갱신, 요청 상태의 조건부 전이, 잠금 대상·순서와 재시도/충돌 처리 |
| 마감·보관·발송 | 각 상태를 구분한 조회 계약, 보관 파일 식별과 발송 건 연결, 최초 발송과 전환 정정본의 중복 방지, 파일 저장·DB 기록 사이 실패 복구 |
| 초기 전환 | 기존 발송 월 등록과 신규 수동 마감의 구분, 적용 대상 한정, 불확실한 발송 확인 및 원본 파일 미확보 항목의 처리 기록 |

현재 마지막 Flyway 파일은 `V14__report_dispatch_optimistic_lock.sql`이다. 구현 시 다시 목록을 확인해 다음 버전을 배정하며, 원 세션에서 되돌린 V15 초안을 그대로 적용하지 않는다.

## 5. 정합성·동시성·발송의 안전장치

| 경쟁 상황 | 보장해야 하는 결과 |
| --- | --- |
| 동시 출근 | 같은 근무일에 한 기록만 저장된다. 기존 UNIQUE 제약을 유지한다. |
| 동시 퇴근 | 같은 기록을 한 번만 종료한다. 조건부 UPDATE와 영향받은 행 수 검사를 유지한다. |
| 새 출근과 이전 근무의 퇴근 | 일반 퇴근 대상 선택과 실제 갱신 사이의 변경을 검출한다. |
| 같은 기록의 동시 신청 | 대기 요청 하나만 생성된다. |
| 승인·반려·취소 경쟁 | 하나의 상태 전이만 성공한다. |
| 승인과 원본 변경 | 다른 근태 행의 변화는 무관하다. 같은 대상 행이 바뀌면 승인으로 덮어쓰지 않는다. |
| 담당자 변경과 요청 생성 | 대기 요청이 있는 담당자 관계가 바뀌지 않도록 한다. |
| 마감과 신청·승인·근태 쓰기 | 검증 직후 새 요청이나 변경이 끼어들어 마감 조건을 깨지 못하게 한다. |
| 수동·예약 보고서 발송 경쟁 | 기존 선점·월별 중복 방지 규칙을 유지한다. |

잠금 대상과 순서는 공통으로 설계해야 한다. 버전 컬럼 추가만으로 모든 경쟁이 해결된다고 가정하지 않는다. JPQL bulk UPDATE는 버전을 자동 처리하지 않을 수 있으므로 기존 퇴근 쓰기 경로도 함께 확인한다.

승인 시 원본 갱신과 요청 처리·이력 저장을 같은 DB 트랜잭션으로 묶는다. 하나라도 실패하면 전체를 롤백한다.

### 5.1 승인 시 재검증과 현재 구현의 주의점

- 신청 때 확인했더라도 승인 트랜잭션에서 처리자의 권한·지정 관계, 요청의 `PENDING` 상태, 원본 버전, 연차 여부, 마감 범위, 제안 시각과 후속 실제 근무를 다시 검사한다. 그 사이 새 출근이 생겼다면 원본 버전이 같아도 후속 근무 경계가 달라질 수 있다.
- 다른 기록의 일반 퇴근은 대상 원본의 변경으로 취급하지 않는다. 예를 들어 9월 2일 정정 대기 중 9월 6일 기록을 퇴근 처리해도, 9월 2일 원본 버전 충돌이 되어서는 안 된다. 신청 날짜 자체로 충돌을 판단하지 않는다.
- 같은 대상 원본이 바뀌었다면 승인을 적용하지 않고 최신 정보를 재조회하게 한다. 충돌을 업무상 반려와 혼동하거나 자동으로 `REJECTED`로 바꾸지 않도록 오류·상태 계약을 명시한다.
- 현재 `updateWorkEndTimeIfOpen()`은 `@Modifying(clearAutomatically = true)`를 사용한다. 이를 정정 처리에서 재사용하면 관리 중인 요청 엔티티도 분리될 수 있으므로 flush·clear 순서와 이력 저장 누락을 검증한다.
- 근무 분은 현재 `Duration.between(...).toMinutes()`의 분 미만 절삭을 유지한다. 화면에서 반올림한 값으로 저장하거나 현지 시각끼리 빼서 UTC 경과시간과 다른 값을 만들지 않는다.
- 현재 `AuthController`는 로그인 당시 역할을 세션에 저장하고 `AuthInterceptor`가 이를 읽는다. `/api/auth/me` 재조회만으로 서버의 모든 권한 검사가 갱신된다고 가정하지 않는다. 역할·담당자 변경 후 이전 세션으로 승인·마감하는 우회를 막을 최신 권한 확인 또는 세션 갱신/무효화 방식을 기술 설계한다.
- 원 세션에서 지적한 쿠키 인증 변경 API의 CSRF 검토를 유지한다. 현재 확인한 `WebConfig`·`AuthInterceptor`에는 전용 검사가 없고 운영 쿠키에는 `SameSite=Lax`가 설정돼 있다. 정정·승인·담당자 지정·마감 경로에 필요한 방어와 검증을 설계하며, 역할 검사만으로 CSRF가 해결된다고 간주하지 않는다.

### 5.2 마감 이후 발송과 참고용 집계

월 마감은 먼저 DB에 커밋한 다음 보고서를 생성·발송한다. 메일과 공휴일 API 호출을 마감 트랜잭션 안에 넣지 않는다. 커밋 후 발송 전에 프로세스가 중단되면 기존 수동 발송 경로로 복구할 수 있어야 한다.

기존 발송기는 매월 1~3일에 예약 재시도를 수행하고, 관리자 수동 재실행 API도 제공한다. 예약·수동·마감 직후 발송 모두 동일한 마감 확인과 발송 선점 경로를 거친다. 미마감과 실제 발송 장애를 사용자에게 구분하여 보여준다.

`DELIVERY_COMMITTED`는 수신 결과가 불확실할 수 있는 보호 상태다. 이 경우 기존처럼 자동 재발송을 막고 수동 확인한다. SMTP와 DB 사이의 엄밀한 exactly-once를 보장한다고 표현하지 않는다.

마감 전 조회·Excel은 승인 전 원본 값으로 집계한다. 미퇴근의 현재 저장값 `workingMinutes = 0`은 근무하지 않았다는 확정값이 아니며, 완료 기록의 대기 정정은 기존 과대·과소 근무 분을 그대로 포함할 수 있다. 참고용 표시와 미해결 정보로 이를 드러내고, 신청한 값을 임시로 원본 집계에 섞지 않는다.

현재 Excel의 “퇴근 미마감 0건 — 대상 월의 출근 기록이 모두 마감되었습니다.” 문구는 종료 시각 누락이 없다는 뜻이다. 새 월 마감 완료와 같지 않으므로 대기 요청·수동 월 마감·발송 여부를 구분하도록 문구와 응답을 맞춘다. 기존 미퇴근 조회를 먼저 하는 보고서 생성 순서만으로 정정과 마감의 경쟁이 해결됐다고 가정하지 않는다.

## 6. 구현 단계와 의존성

**번호는 작업 묶음이지 모든 작업을 완전히 순차 실행하라는 의미가 아니다.** 정책·계약이 필요한 부분은 먼저 확정하고, 독립적인 작업은 병행할 수 있다. 다만 사용자 승인 없이 에이전트 병렬 작업을 시작한다는 의미는 아니다.

| 단계 | 작업 | 선행 조건 | 완료 기준 |
| --- | --- | --- | --- |
| 1 | 정책과 1차 범위 최종 검토 | 없음 | 운영 정책 확정 완료. 3장의 초기 전환 대상·운영 절차를 실제 데이터에 맞춰 준비한다. |
| 2 | API·상태 전이·동시성 계약 설계 | 1 | `openapi.yml`, 오류 계약, 쓰기 경쟁 처리 원칙을 확정한다. |
| 3 | DB 마이그레이션·도메인·저장소 | 2 | 제약·상태 전이·버전 처리와 가까운 테스트를 준비한다. |
| 4 | 상위 승인자 권한·담당자 지정 | 3 | 본인 기능, 대상별 승인 권한, 대기 중 지정 변경 방지를 검증한다. |
| 5 | 출퇴근 변경·정정 요청 유스케이스 | 3, 승인 기능은 4 | 신청·승인·반려·취소와 일반 퇴근 경쟁을 검증한다. |
| 6 | 월 마감·보고서 연결 | 3, 5의 쓰기·요청 계약 | 마감 경쟁, 잠금, 커밋 후 발송, 재시도를 검증한다. |
| 7 | 프론트엔드 화면·상태 연결 | 착수는 2, 완성은 4~6 | 역할별 신청·승인·마감·발송 화면과 오류 처리가 동작한다. |
| 8 | 통합 검증·운영 문서 | 3~7 | backend check, frontend lint/build, 브라우저·MySQL 검증 결과를 기록한다. |

### 병행할 수 있는 작업

- 3단계 이후 4단계 권한 처리와 5단계의 순수 출퇴근 규칙·신청/취소 부분은 병행할 수 있다. 승인 기능의 완성은 권한 처리를 기다린다.
- 2단계에서 API가 확정되면 7단계의 화면·hook 구조를 먼저 작성할 수 있다. 실제 동작 확인은 backend 연결 후 수행한다.
- 6단계의 월 마감 모델·검사 준비는 앞서 진행할 수 있으나, 5단계 쓰기 경로와 통합하기 전에는 마감 안전성을 완료로 보지 않는다.
- 각 단계의 단위·저장소·컨트롤러 테스트는 구현과 함께 작성한다. 모든 테스트를 8단계까지 미루지 않는다.

### 순서대로 끝내야 하는 경로

```text
정책 확인(1)
→ API·경쟁 처리 계약(2)
→ 데이터·도메인 기반(3)
→ 권한 및 정정 쓰기 경로 통합(4·5)
→ 마감·발송 통합(6)
→ 화면까지 연결한 최종 검증(7·8)
```

backend 도메인·권한, frontend, 검증의 담당 작업을 나눌 때도 같은 파일이나 같은 쓰기 규칙을 중복 변경하지 않도록 범위를 정한다.

### 여러 세션으로 구현할 경우의 권장 분담

원 세션의 권장안은 **기술 계약을 한 세션에서 정리 → backend와 frontend 두 세션으로 병행 → 통합 검증**이다. 분담 권장안이며 이 문서 작성으로 새 세션이나 병렬 에이전트 실행을 승인한 것은 아니다.

| 담당 | 작업과 소유 범위 | 인계 조건 |
| --- | --- | --- |
| 기술 계약 | 4.4절의 API·DB·상태 전이·동시성 계약 | 경로·응답 예시·오류·역할별 권한·공통 잠금 원칙을 문서화 |
| Backend | 도메인·DB·권한·출퇴근·정정·마감·발송 및 관련 테스트 | 함께 쓰는 근태 갱신·잠금 규칙을 일관되게 검증 |
| Frontend | 확정 API 기반 화면·hook·역할별 접근·충돌 후 재조회 | backend 연결 전 확인과 연결 후 확인을 구분 |
| 통합 | 변경 통합, 전체 검사·MySQL·브라우저 검증, 운영 안내 | 실제 실행 결과·미검증 항목·초기 전환 준비 상태 기록 |

- Backend를 출퇴근·정정·월 마감별 독립 세션으로 다시 쪼개는 것은 우선 권장하지 않는다. 같은 행과 잠금 규칙의 결합도가 높기 때문이다. 앞 절의 병행 가능성은 논리적 의존성을 설명한 것이며, 기능별 독립 구현을 권장한다는 뜻은 아니다.
- `openapi.yml`과 생성 타입 `frontend/src/api/schema.d.ts`는 한 계약 담당자가 함께 관리한다. 계약 변경 시 두 구현 세션에 공유하고 생성 타입을 갱신한다.
- 병행할 때는 별도 작업 디렉터리 또는 Git worktree와 수정 파일 범위를 정한다. 공통 파일을 동시에 수정하지 않는다.
- 각 인계에는 기준 커밋·변경 목록, 확정/변경된 계약, 실행한 검증과 건너뛴 검증, 미완료 사항을 남긴다. 테스트는 각 담당 구현에 포함하고 통합 단계에 모두 미루지 않는다.

## 7. 검증 시나리오와 명령

### 7.1 회귀·경계 테스트

- 과거 미퇴근이 남아 있어도 새 근무일 출근은 성공하고, 같은 근무일 출근은 중복 거부한다.
- 야간근무, 정확히 24시간, 24시간을 조금 초과하는 경계를 고정 `Clock`으로 검증한다.
- 최신 근무 퇴근 후 재클릭해도 과거 미퇴근을 종료하지 않는다.
- 조회 월 밖의 후속 근무도 이전 미퇴근의 정정 필요 판정에 반영한다.
- 신청·반려·취소는 원본을 바꾸지 않고, 승인만 종료 시각·근무 분을 반영한다.
- 빈 사유, 출근 이전, 미래 시각, 다음 근무와 중첩, 연차 정정을 거부한다.
- 반려 사유는 필수이며 승인 의견은 선택 사항이다.
- 승인 정정의 24시간 초과 근무는 허용한다. UTC 저장·기록 시간대·근무일을 유지한다.
- 타인 신청·조회, 자기 승인, 미지정 또는 다른 담당자의 승인, 상위 승인자의 관리자 기능 접근을 거부한다.
- 취소·반려 후 재신청, 같은 기록 반복 정정, 전후 값·처리자 이력 보존을 확인한다.
- 동시 출근·퇴근·신청·승인·취소·담당자 변경·마감을 검증한다.
- 대기 요청에 영향을 주는 역할 변경·비활성화를 거부하고, 처리 후에는 허용한다. 요청 생성과 역할 변경의 경쟁도 검증한다.
- 원본 또는 이력 저장 실패 시 승인 전체가 롤백된다.
- 미해결 기록은 마감을 막고, 마감 후 모든 관련 쓰기 경로를 차단한다.
- 월말·연말과 집계의 전월 참조를 검증한다. 이미 마감한 보고서의 입력이 변경되지 않는다.
- 한국 시간의 월 경계에서 과거 월만 마감할 수 있고 현재·미래 월은 거부한다.
- 전월 참조 기간의 기록 추가·삭제·연차 쓰기도 보호하며, 초기 전환 월 간 기간 겹침을 검증한다.
- 발송 실패·커밋 직후 중단·재시도·동시 발송·불확실한 수신 상태를 검증한다.
- 보관 실패 시 미발송, 재시도 시 동일 파일 사용, 직원·팀·공휴일 변경 후에도 확정본 다운로드가 보관본과 같음을 검증한다.
- 미마감 다운로드는 참고용으로 표시하고, 보관 파일 접근에 기존 보고서 권한을 적용한다.
- 초기 전환의 정정 승인·원본 보존·정정본 별도 발송·중복 방지·불확실한 기존 발송 확인을 검증한다. 전환 예외로 신규 마감 월을 다시 수정할 수 없어야 한다.
- 기존 연차, 초과근무, Excel, 보고서 발송 테스트도 회귀 검증한다.

세션 초기 분석에서 도출한 다음 시나리오도 빠뜨리지 않는다.

- 출근과 동일 시각은 0분, 59초는 0분, 60초는 1분으로 계산된다. 날짜·오프셋 입력, DST, MySQL 시각 정밀도를 검증한다.
- 신청 후 직원의 현재 시간대가 달라져도 대상 기록의 `workDate`·`workZone`과 월 귀속은 바뀌지 않는다.
- 신청 후 후속 출근이 생긴 경우 승인 시 중첩을 다시 검사한다. 다른 행의 정상 퇴근은 원본 버전 충돌로 처리하지 않는다.
- 오래된 기록도 마감 보호 범위 밖이면 기간 경과만으로 거부하지 않는다. 반대로 전월 말 기록은 자기 월이 미마감이어도 다른 마감 보고서의 입력 범위에 들면 정정할 수 없다.
- 존재하지 않는 대상, 처리 완료 요청의 재처리, 미인증 요청, 직접 API를 호출한 권한 우회, 이전 세션 권한과 CSRF 방어를 검증한다.
- 일반 퇴근·정정 승인에서 버전이 일관되게 갱신되고, bulk UPDATE의 clear 이후에도 요청 상태·이력이 함께 커밋되거나 롤백된다.
- 미퇴근 0건이어도 대기 정정 또는 수동 월 마감 미완료를 완료로 표시하지 않는다. 미퇴근 0분과 승인 전 기존 근무 분을 확정본으로 오인하게 하지 않는다.
- 승인 후 본인 월 합계·초과근무·참고용 Excel을 확인하고, 영향을 받는 인접 월과 근태·요청·이력 Query 캐시를 갱신한다. 화면 충돌 시 최신 값을 다시 조회한다.

### 7.2 실행 및 결과 보고

1. 변경한 도메인·서비스·저장소·컨트롤러 테스트부터 실행한다.
2. backend 최종 검증은 Java 21에서 `./gradlew check`로 수행한다.
3. MySQL/Flyway·DB 정밀도·잠금·제약은 Docker가 있는 환경에서 Testcontainers로 검증한다. 건너뛴 테스트는 통과로 보고하지 않는다.
4. Node.js 22·pnpm 10에서 API 변경 후 `pnpm --dir frontend gen:api`를 실행한다.
5. `pnpm --dir frontend lint`, `pnpm --dir frontend build`를 실행한다.
6. 브라우저에서 각 역할의 정상·로딩·오류·권한·충돌·마감·발송 상태를 확인한다.
7. 필요한 README·운영 안내를 갱신하고 실제 실행 결과와 미검증 항목을 구분한다.
