# Agent Development Guide

A file for [guiding coding agents](https://agents.md/).

Development guidelines for an internal attendance management service covering clock-in/out, annual leave, monthly overtime calculations, and Excel reports.
Run commands from the repository root unless stated otherwise. Use the current code, build configuration, and tests as the source of truth when documentation differs.

## Instruction Files

- This root-level `AGENTS.md` uses the standard filename for automatic discovery by Codex.
- Claude Code reads `CLAUDE.md`. To share these instructions with Claude Code, a `CLAUDE.md` file can import this file using `@AGENTS.md` outside a code span or fenced code block.
- Before working on the frontend, also read `frontend/CLAUDE.md` and follow its rules for that area.

## Development Environment and Commands

- Backend: Java 21, Spring Boot 3.5.5, Gradle Wrapper 8.7. Use `./gradlew` instead of a system Gradle installation.
- Frontend: React 18, TypeScript strict mode, Vite, Mantine 7, TanStack Query 5.
- Use Node.js 22 and pnpm 10 to match `.github/workflows/ci.yml`. Do not introduce npm/yarn or additional lockfiles.
- Development uses an in-memory H2 database whose schema is created at startup and dropped at shutdown. Production uses MySQL and Flyway.

| Purpose | Command |
| --- | --- |
| Run the development backend (port 8080) | `./gradlew bootRun --args='--spring.profiles.active=dev'` |
| Build and check the backend | `./gradlew build` |
| Build the executable JAR | `./gradlew bootJar` |
| Run backend CI checks: tests and OpenAPI validation | `./gradlew check` |
| Run all backend tests | `./gradlew test` |
| Run a specific test class | `./gradlew test --tests 'com.company.officecommute.service.commute.CommuteHistoryServiceTest'` |
| Run MySQL integration tests (requires Docker) | `./gradlew test --tests '*MySqlIntegrationTest'` |
| Validate the OpenAPI specification | `./gradlew openApiValidate` |
| Install frontend dependencies | `pnpm --dir frontend install --frozen-lockfile` |
| Run the development frontend (port 5173) | `pnpm --dir frontend dev` |
| Lint the frontend | `pnpm --dir frontend lint` |
| Check TypeScript and build the frontend | `pnpm --dir frontend build` |
| Regenerate frontend OpenAPI types | `pnpm --dir frontend gen:api` |

For development, set `PUBLIC_API_SERVICE_KEY` through an environment variable or the root `.env` file. `application.yml` loads `.env`; see `application-dev.yml` for the holiday API URL and timeout settings. Live holiday API requests require a valid key.

## API Contracts and Frontend

- When changing endpoints or DTOs, update `openapi.yml` first and keep controllers, DTOs, and tests consistent with it. Backend code generation is currently unused; specification validation alone does not verify that the implementation matches the contract.
- Keep API endpoints under `/api/**` to avoid collisions with frontend SPA routes.
- After API changes, run `pnpm --dir frontend gen:api` to regenerate `frontend/src/api/schema.d.ts`. Do not edit this file manually.
- Follow the existing `ErrorResult`, `ValidationErrorResult`, and `GlobalExceptionHandler` contracts in `global/exception/`. Reflect new error codes in frontend user-facing messages and form field error handling.
- Place frontend HTTP calls in resource-specific TanStack Query hooks, using the typed `api` client in `frontend/src/api/client.ts` and `unwrap()` from `frontend/src/lib/errors.ts`.
- Authentication uses the `JSESSIONID` session cookie. Preserve `baseUrl: ''`, `credentials: 'include'`, and the development server's `/api` proxy.
- Restore authentication state and roles through `GET /api/auth/me`. Preserve role-based routing and the policy of not retrying 401/403 responses. Check backend authorization as well when changing access controls.

## Backend Rules

- Follow the existing `controller → service → repository` structure and keep domain rules in `domain`. Do not implement business rules solely in controllers or the frontend.
- Use the injected `Clock` for time-dependent logic. Use fixed instants in tests to reproduce day and month boundaries.
- Preserve UTC storage for clock-in/out timestamps and calculate the work date using the employee's time zone at clock-in. Do not reinterpret historical records using the employee's current time zone or the server's default time zone.
- Use database UNIQUE constraints as the final consistency boundary for duplicate clock-ins and annual leave registrations, and map those conflicts to HTTP 409. Do not classify every database error as a duplicate.
- Preserve conditional UPDATE statements and affected-row checks for clock-out. Do not rely solely on a read followed by a save to handle concurrent requests.
- Preserve the `HolidayCalendar` abstraction for holiday data. Do not hide external API failures by returning an empty holiday list or a successful overtime calculation.
- For schema changes, add the next versioned SQL migration under `src/main/resources/db/migration/` instead of editing already-applied migrations. Check consistency with entities, constraints, and development seed data.
- Follow the naming, indentation, and import style of surrounding code. Do not assume an unconfigured formatter exists or reformat unrelated files.

## Validation

- Start with tests closest to the changed behavior. Extend existing tests or add regression tests for bug fixes and consistency changes.
- Run `./gradlew check` as the final validation for backend code changes. Cover relevant boundary conditions when changing time zones, concurrency, or database constraints.
- `*MySqlIntegrationTest` uses Testcontainers and is skipped when Docker is unavailable. Do not report skipped tests as passed. Validate MySQL/Flyway changes in an environment with Docker.
- Validate frontend changes with `pnpm --dir frontend lint` and `pnpm --dir frontend build`. There is currently no separate frontend `test` script. For UI changes, check loading, error, and role-specific behavior on the affected routes in a browser.
- For documentation-only changes, verify paths, commands, configuration references, and the diff. Distinguish checks that ran from checks that could not run when reporting results.

## Configuration and Operations

- Supply secrets through environment variables. Do not copy `.env` contents, API keys, database or email passwords, or session cookies into code or documentation.
- Follow existing mock and local test server patterns when testing holiday API and email integrations.
- Before deployment work, read `docs/DEPLOYMENT.md`, `docs/CD_RUNBOOK.md`, and the current workflows.
- Update this document and the relevant README when structure, commands, or contracts change. Link to detailed designs and historical records; keep this file focused on instructions needed repeatedly.
